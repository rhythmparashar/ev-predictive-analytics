## Phase 1 — Data Foundation
> **Status: ✅ Complete and Stable**

### What it does
Raw CSV → Silver parquet. One command per date. Deterministic and idempotent.

### Pipeline
```
Raw CSV
  → Column standardisation
  → Timestamp parsing (HH:MM:SS → UTC datetime)
  → Validation + quality_flag bitmask
  → Write raw_parquet
  → Resample to 1 Hz (by signal class)
  → Fault alignment (binary fault_* columns)
  → Trip segmentation (trip_id)
  → Write silver
  → Write manifest JSON
```

### Key files
| File | Purpose |
|---|---|
| `ingestion/ingest.py` | Pipeline entry point per vehicle per day |
| `ingestion/validators.py` | quality_flag bitmask — 7 flag types |
| `ingestion/resampler.py` | 1 Hz resampling by signal class (fast/slow/status) |
| `ingestion/faults.py` | Aligns fault log windows → binary fault_* columns in silver |
| `ingestion/trip_segmentor.py` | Trip start/end detection, cross-day state file |
| `ingestion/io.py` | All file I/O, atomic writes (tmp → rename) |
| `scripts/run_day.py` | CLI entry point: `python run.py ingest --dt YYYY-MM-DD` |

### Outputs
```
data/raw_parquet/dt=YYYY-MM-DD/vehicle_id=EV01.parquet
data/silver/dt=YYYY-MM-DD/vehicle_id=EV01.parquet
  ├── telemetry signals
  ├── quality_flag       (bitmask)
  ├── trip_id            (EV01_000001, EV01_000002, ...)
  ├── fault_*            (one binary column per fault code)
  └── fault_any          (1 if any fault active)
data/reports/dt=YYYY-MM-DD.json
data/state/open_trips.parquet   (cross-day trip continuity)
```

### quality_flag bitmask
| Bit | Value | Meaning |
|---|---|---|
| 0 | 1 | Interpolated (fast signal) |
| 1 | 2 | Forward-filled (slow/status signal) |
| 2 | 4 | Gap inserted (missing source row) |
| 3 | 8 | Soft range breach |
| 4 | 16 | Hard range breach |
| 5 | 32 | Time anomaly |
| 6 | 64 | Sensor flatline |

### Properties
| Property | Status |
|---|---|
| Stable | ✅ |
| Deterministic | ✅ |
| Idempotent (rerun = same output) | ✅ |
| Cross-day trips | ✅ |
| New vehicle = zero code changes | ✅ |
| Fault alignment in silver | ✅ |

## Phase 2 — Gold Feature Engineering
> **Status: ✅ Complete and Stable**

### What it does
Silver → Gold. Computes ML-ready features per trip, writes partitioned parquet.

### Pipeline
```
Silver parquet
  → Quality filter: (quality_flag & 52) == 0
  → Trip-level streaming (one group at a time)
  → Rolling features (30s, 60s, 300s, 600s windows)
  → Physics features (voltage imbalance, thermal gradient, efficiency proxy)
  → Lag features (60s, 300s, 600s)
  → SOC target label: y_soc_t_plus_300s = soc_pct.shift(-300)
  → label_available flag
  → Write window_features (partitioned by trip, one part-XXXXXX.parquet per trip)
  → Write trip_features (one row per trip)
  → Write daily_stats
  → Write manifest JSON
```

### Key files
| File | Purpose |
|---|---|
| `features/pipeline.py` | Main Gold builder per vehicle per day |
| `features/rolling.py` | Rolling mean/std/min/max |
| `features/physics.py` | Derived physics variables |
| `features/lags.py` | Lag features |
| `features/trip_agg.py` | Per-trip aggregations |
| `scripts/run_gold_day.py` | CLI entry point: `python run.py gold --dt YYYY-MM-DD` |

### Outputs
```
data/gold/window_features/dt=YYYY-MM-DD/vehicle_id=EV01/
  part-000001.parquet ... part-XXXXXX.parquet   (one per trip)
  ├── telemetry signals + rolling + lag + physics features
  ├── quality_flag, trip_id, fault_any
  ├── y_soc_t_plus_300s   (target)
  └── label_available
data/gold/trip_features/dt=YYYY-MM-DD/vehicle_id=EV01.parquet
data/gold/daily_stats/dt=YYYY-MM-DD/vehicle_id=EV01.parquet
data/reports/gold/dt=YYYY-MM-DD/vehicle_id=EV01.json
```

### Properties
| Property | Status |
|---|---|
| Silver never modified | ✅ |
| Streaming per trip (low RAM) | ✅ |
| Atomic directory writes | ✅ |
| Column projection (schema-safe) | ✅ |
| Target label + label_available flag | ✅ |

## Phase 3 — Production ML Pipeline
> **Status: ✅ Complete and Verified**
> **Active model:** `v2__2026-03-13__fc0cd5ed`
> **Val MAE:** 0.441% SOC — **EXCELLENT** (threshold: < 0.5%)

### What it does
Gold → XGBoost model. Full train/eval/versioning/drift pipeline. Two operating modes:
- `train` — full retrain, new versioned run folder
- `eval` — inference only on a new day, no retraining

### Folder structure
```
ev-telemetry-ml/

├── tasks/
│   └── soc_forecast/
│       ├── feature_set.py     ← canonical FEATURES list (single source of truth)

│       ├── train.py           ← training entry point

│
├── training/
│   ├── dataset.py             ← Gold loader, quality filter, derived features

│   └── artifacts.py           ← versioned run folder save/load
│
├── evaluation/
│   └── metrics.py             ← MAE, RMSE, MAPE, per-group, SOC buckets, baselines
│
├── monitoring/
│   └── drift.py               ← PSI + KS test per feature vs training baseline
│
├── models/
│   └── soc_forecast/
│       └── v2__2026-03-13__fc0cd5ed/
│           ├── model.json

│   └── drift_reports/

│       └── dt=YYYY-MM-DD_eval.json     ← eval + drift combined
│
└── run.py                     ← single CLI entry point
```

### Commands
```bash
# Full pipeline for a new date
python run.py ingest --dt YYYY-MM-DD
python run.py gold   --dt YYYY-MM-DD

# Retrain (edit tasks/soc_forecast/config.yaml dates first)
python run.py train  --task soc_forecast

# Inference-only eval on new day (no retraining)
python run.py eval   --task soc_forecast --dt YYYY-MM-DD

# Pin specific run
python run.py eval   --task soc_forecast --dt YYYY-MM-DD --run-id v2__2026-03-13__fc0cd5ed

# Drift check only
python run.py drift  --task soc_forecast --dt YYYY-MM-DD

# Backfill
python run.py ingest --backfill --start 2026-01-01 --end 2026-03-13
```

### Drift monitoring — v2 eval results

Drift is flagged on every `eval` call. Results on the two val days and one out-of-sample day:

| Date | Stable | Monitor | Drift | Overall | Val MAE |
|---|---|---|---|---|---|
| 2026-03-04 (out-of-sample) | 5 | 0 | 56 | DRIFT | 0.489% |
| 2026-03-14 (val) | 5 | 0 | 56 | DRIFT | 0.377% |
| 2026-03-15 (val) | 5 | 0 | 56 | DRIFT | 0.521% |

> **Important:** 56/61 features flagging DRIFT does not indicate model failure. MAE remains excellent (0.377–0.521%) despite the drift flag. The drift is driven by known structural causes — see table below. PSI thresholds are conservative; the model is robust to this level of distributional shift.

**Drift root causes — categorised**

| Category | Features affected | Root cause | Action |
|---|---|---|---|
| Cumulative counter | `total_kwh_consumed` + lags (PSI=11–12) | Monotonically increasing odometer — always drifts | **Drop before next retrain** |
| SOC regime shift | `soc_pct` + all derivatives (PSI=2–6) | Val days operating at different SOC range than training | Expected — monitor MAE not PSI |
| Battery temperature | `avg_battery_temp_c` + derivatives (PSI=5–10) | Seasonal / time-of-day ambient shift | Monitor — consider adding temp normalisation |
| Voltage | `stack_voltage_v`, `max_cell_voltage_v` (PSI=3–4) | SoC-linked voltage shift | Follows SOC drift — expected |
| Cell imbalance | `cell_voltage_delta_v` (PSI=6–11) | Battery ageing signal emerging in March data | **Watch — potential early degradation indicator** |
| Load profile | `battery_current_a`, `output_power_kw` (PSI=1–3) | Duty cycle differences between train and val days | Expected — excavator workload varies |
| Fault flags | `fault_any`, `is_parked_charging` (PSI=0) | Binary features — zero variance in val | Drop or recode as engineered features |

**Known permanent drifters — drop before next retrain:**
- `total_kwh_consumed` + `_lag_60s` + `_lag_300s` — cumulative odometer, PSI=11–12 by design
- `fault_any` — near-zero variance, PSI=0, ks_p=1.0 on some days
- `is_parked_charging` — near-zero variance, PSI=0, ks_p=1.0

> After dropping these, feature count drops from 61 → ~55, and drift reports will be cleaner and more actionable.

## Phase 4 — Model Improvement + Explainability
> **Status: ⏳ Not started**

### Planned work

**Feature cleanup (do before next retrain — high priority)**
- Drop `total_kwh_consumed`, `total_kwh_consumed_lag_60s`, `total_kwh_consumed_lag_300s` — cumulative counter, PSI=11–12 permanently
- Drop `fault_any`, `is_parked_charging` — near-zero variance, PSI=0, adds noise not signal
- Drop `motor_temperature_c` family if still all-zero on EV01
- Result: 61 → ~54 features, cleaner drift reports, faster training

**SHAP explainability**
- Per-prediction feature attribution
- SHAP summary plot — global feature drivers across all val trips
- SHAP waterfall plots — explain individual trips (useful for EV01_001454 high-error investigation)
- Determine whether `stack_voltage_v`, `output_power_kw`, `battery_current_a` are genuinely contributing or masked by SOC autocorrelation
- Add `shap>=0.44` to `requirements.txt`

**Hyperparameter tuning**
- Optuna Bayesian search over `max_depth`, `learning_rate`, `subsample`, `min_child_weight`, `n_estimators`
- Walk-forward cross-validation (train month N, val month N+1)
- Target: maintain Excellent status (MAE < 0.5%) with fewer trees (faster inference)
- Add `optuna>=3.4` to `requirements.txt`

**Fault-aware evaluation**
- Separate MAE for `fault_any == 0` vs `fault_any == 1` rows
- Quantify whether active faults degrade SOC prediction accuracy
- If MAE degrades > 0.3% under fault conditions: train fault-conditioned model variant

**Cell imbalance monitoring**
- `cell_voltage_delta_v` showing PSI=6–11 in March — highest drift of any physics feature
- This is a potential early battery degradation signal, not just a regime shift
- Track `cell_voltage_delta_v` trend weekly; if mean shift > 20% sustained, flag for BMS review

**Multi-vehicle generalisation**
- When EV02 data available: train on EV01, test on EV02 zero-shot
- Measure cross-vehicle MAE degradation
- Decision point: one shared model vs per-vehicle models based on MAE gap

**Retrain trigger**
- Rolling 7-day MAE tracked in `data/drift_reports/`
- If rolling MAE exceeds 1.0%: flag for retrain automatically
- Implement in `monitoring/health.py`
